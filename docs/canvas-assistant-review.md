# 原有助手实现评审

评审基线：主分支 `ae83608`，重点是此前提交的蛙导 M0，而非本轮新增的画布编排功能。

## 总体判断

作为“把一句话翻译成几个安全画布操作”的 M0，边界清楚，基础合格。
作为“看懂项目进度，告诉用户下一步，并替他推进创作”的助手，还缺上下文、编排和执行闭环。
这两种目标应当区分，不能因为三个命令可用，就认为创作助手已经完成。

## 做得好的地方

1. 后端与前端各有命令白名单，模型输出不能直接变成任意代码。
2. 命令规格直接生成提示词，减少文档、提示词与实际工具能力不一致的问题。
3. 复用节点工厂、画布 store 和连线类型注册表，执行后回读，避免完全不检查就宣称成功。
4. 节点摘要优先保留选中内容，避免用户说“这个”时目标被截断。
5. 对话与生成分开限流，免费对话不挤占生成次数；平台 token 用量也有日志。
6. 有异常 JSON、非法命令、真实模型意图识别等测试，并且明确把能力限定为 M0。

## 具体问题

| 问题 | 代码依据 | 影响 |
| --- | --- | --- |
| 上下文只有 ID、类型、名称、状态，没有内容、分镜、连接与素材准备信息 | `assistant.Context / CanvasNode`、`buildAssistantContext` | 可以找到某个节点，却无法可靠判断创作进度和下一步 |
| 没有新节点临时引用或命令结果绑定 | `create_node` 不返回可供后续命令引用的 ID；`connect_nodes` 只接受已有 ID | “新建两个节点并连起来”无法稳定在一轮完成 |
| 异步回复未绑定发问时的项目 | 原 `assistantStore.send` 回复后直接执行，命令读取当前画布 | 等待中切换项目，旧请求可能操作新项目；本轮已增加保护与回归测试 |
| 连线仅检查类型、自环和重复，没有检查循环 | `connectNodesCommand` 和 `canvasStore.connectNodes` | 可以构造多节点循环，之后生成引擎才报错 |
| 连上上游后没有同步实际输入引用 | 原 `connectNodesCommand` 只建边，而 `ScriptExecutor` 要求 `mentions` 中明确引用上游文本 | 画布看似连好了，生成时仍会报“未通过 @ 引用使用剧本内容” |
| 多命令逐条执行、逐条记历史，单条失败后继续 | 原 `executeCommands` | 用户得到半套流程；一次撤销也不能回退整轮助手操作 |
| 每条旧消息的“撤销”按钮都调用同一个全局 undo | `undoLast` | 用户手动修改过后，点击较早消息的撤销会撤掉最近的手工操作，容易误解 |
| 提示词要求有命令时先说“已经完成” | 原 `assistantRules` 第 8 条 | 实际命令失败时，回复与执行回执相互矛盾 |
| 模型字段直接接受字符串，没有校验渠道与可用模型 | `updateNodeCommand` | 模型可能编造一个 ID；界面说修改成功，但节点无法生成 |
| 缺少项目会话隔离与对话持久化 | 原 `assistantStore.messages` 是全局内存数组 | 不同项目的历史混在一起，刷新又全部消失 |

“暂时不能生图、导出、发布”本身不是缺陷，是 M0 的明确取舍。
问题是若把 M0 当成完整创作助手推广，用户自然会要求这些闭环能力，体验就会断在最后一步。

## 本轮落实

画布页增加项目级摘要、结构化操作计划、临时节点引用、前后端校验、
类型与环路检查、整轮事务撤销、过期计划拦截、生成报价与 SSE 状态回写；
会话按用户和项目保存在本机。全局问答仍保留原实现，并补上迟到回复的项目切换保护。

继续沿用蛙导名称、免费对话和平台 token 日志，不改变已有节点计费。
生成按当前已准备好的阶段推进；跨阶段自动调度与服务端会话持久化仍是后续工作。
