# 项目卡片封面：改为「最后一次生成视频的素材图」

> 日期：2026-10-28　状态：方案待评审
> 反馈原文：*用户的项目图片目前应该是随机的，用户如果产出多个项目，退出后再次进入平台很难找到自己想要再次创作的项目。用户希望是他最后一个生成视频的素材图。*

---

## 〇、结论速览

1. 「图片随机」不是设计，是 **`projects.cover_url` 从来没有被自动写过**，前端对空值兜底成了 `picsum.photos` 随机图库图。
2. 修法：**视频生成成功那一刻，服务端把这次送进视频节点的第一张素材图写进 `cover_url`**。零额外下载、零额外模型调用、失败不影响出片。
3. 顺带修第二个同样致命的原因：**`projects.updated_at` 不随画布编辑/生成更新**，所以「最近项目」实际按创建时间排 —— 最近在做的项目会沉底。

---

## 一、问题定位

### 1.1 数据链路断点：`cover_url` 全库只有一条写入路径

`server/internal/model/model.go:52` 定义了字段：

```go
CoverURL string `gorm:"size:500" json:"cover_url"`
```

全仓搜索 `CoverURL` / `cover_url` 的**写入**只有一处 —— `server/internal/handler/show_handler.go:280`，即用户**发布作品并手动上传封面**时同步一份到项目：

```go
// 如果 show 关联了项目，同步更新项目封面
project.CoverURL = result.URL
_ = h.projectRepo.Update(c.Request.Context(), project)
```

结论：**没走过「发布 + 传封面」的项目，`cover_url` 恒为空串**。而绝大多数用户的项目都处于"做了一半、没发布"状态 —— 也就是反馈里那批项目。

### 1.2 前端把空封面兜底成随机图

`web/src/components/project/ProjectCard.tsx:29-35`：

```tsx
{project.coverUrl ? (
  <img src={project.coverUrl} ... />
) : (
  <div className="...">
    <img src={`https://picsum.photos/200/150?random=${project.id}`} ... />
  </div>
)}
```

`picsum.photos` 是公共图片库。`?random=<id>` 让同一项目结果稳定，但**内容与项目毫无关系**：用户打开首页看到的是几张互不相干的风景照。项目越多，越无法区分 —— 这正是"找不到想再创作的项目"的直接原因。

附带的可用性风险：`picsum.photos` 是境外域名，中国大陆访问可能超时或很慢，卡片会长时间空白。

### 1.3 附带发现：列表排序同样没跟上

- 列表按 `updated_at DESC` 排序：`server/internal/repository/project_repo.go:47`
- 但 `projects.updated_at` 只在**改名**（`project_handler.go:88` → `project_service.go:79`）和**发布传封面**（`show_handler.go:280`）时变化。
- 画布保存链路（`canvas_handler.go:47` → `canvas_service.go:26` → `canvas_repo.go.Save`）只写 `canvases` 表；引擎逐节点落库、生成成功也都不碰 `projects` 表（已确认 `repository` 层其余对 `model.Project` 的引用全是只读 `Select`）。

所以「最近项目」实际是按**创建时间**倒序 —— 昨天刚做了一半的项目，可能排在三个月前建的十几个空项目下面。这一条与封面同等重要，建议同批修。

## 二、方案总览

**核心语句**：视频生成成功的那一刻，把「这次送进视频节点的第一张素材图」写进 `projects.cover_url`。

```
用户点生成
   │
   ├─ VideoExecutor.Execute 收集 imageURLs（mentions 里的图片节点 + 上游兜底 + 白模静帧）
   │
   ├─ 生成 → 下载 → 上传对象存储 → ownVideoURL
   │
   ├─ ★ 写封面：imageURLs[0] → 缩略图 URL → UPDATE projects SET cover_url, updated_at
   │        （与 RecordGeneration 同一位置、同一份 detachedCtx，失败只记日志）
   │
   └─ 返回节点输出 videoUrl → 前端渲染
```

### 2.1 选「输入素材图」而不是「视频抽帧」

| 候选 | 识别度 | 成本 | 可用性 |
| --- | --- | --- | --- |
| **输入素材图（`imageURLs[0]`）** | 高 —— 就是"我上次做这条片子用的那张图"，符合用户心智与反馈原文 | **零**：URL 已在执行器手里，不用下载视频、不用 ffmpeg、不新增存储对象 | 纯文生视频时不存在 |
| 视频首帧抽帧 | 最高 —— 真·成片画面 | 中。但注意：视频字节在 `downloadAndUpload` 里**已经在内存中**（`executor.go:3044`），ffmpeg 抽一帧实际只需百毫秒级 | 恒有 |
| 画布最新一张图 | 中 —— 可能是跟这条视频无关的图 | 零，但需解析画布 | 需解析 |
| 随机图（现状） | **零** | 零 | 恒有 |

因此设计成**兜底链**而不是二选一：

```
① 本次视频节点的第一张输入素材图           → 用它的 640px 缩略图（.thumb.webp）
② 没有输入图（纯文生视频 / 只有参考视频） → 从刚下载的视频字节抽一帧当封面（P1，可选）
③ 仍然拿不到                              → 不写 cover_url，前端渲染确定性占位图（见 §4）
```

### 2.2 为什么不加新列

- 直接覆盖 `cover_url`。发布作品的封面独立存在 `shows.thumbnail_url`（`model.go:208`），`projects.cover_url` 只是项目卡片的展示副本，覆盖它**不影响前台作品页**。
- 语义上也正确：用户要的就是"永远显示最后一次生成视频的素材图"。
- 若将来产品要支持「用户自定义项目封面」，再加 `cover_source`（manual/auto）列，让手动值优先 —— 现在没有这个入口，不预留复杂度。

### 2.3 写缩略图不写原图

卡片高度只有 128px（`h-32`），原图动辄 1.9MB。图上传/生成时后端本来就会顺手写一张 640px webp（`thumbnail.go:15`、`executor.go:2209`、`upload_handler.go:419`），对象命名有约定（`thumbnail.go:43`：`foo/hash.png → foo/hash.thumb.webp`）。封面存这张即可，省约 98% 流量。

必须做**存在性兜底**：老数据可能没有缩略图（上传请求没走完的那批）。用 `storage.ParseObjectName` + `storage.StatObject` 探一下，不存在就回退原图 URL。

## 三、后端改动清单

### 3.1 `server/internal/repository/project_repo.go` — 新增只更新封面的方法

**不要用现有的 `Update`（`db.Save` 整行）**：生成是并发收口的，整行写会把并发的改名/描述覆盖回旧值。

```go
// UpdateCover 只更新封面列，并顺带把 updated_at 推到当前时间。
//
// 为什么不用 projectRepo.Update（整行 Save）：视频生成是并发收口的，
// 同一项目可能有多个节点先后完成，整行写会把并发的改名/描述冲回旧值。
// 顺带更新 updated_at 是刻意的 —— 项目列表按它排序（project_repo.go:47），
// 而它此前不随画布编辑变化，导致「最近项目」名不副实。
func (r *projectRepo) UpdateCover(ctx context.Context, projectID, coverURL string) error {
	res := r.db.WithContext(ctx).Model(&model.Project{}).
		Where("id = ?", projectID).
		Updates(map[string]interface{}{
			"cover_url":  coverURL,
			"updated_at": gorm.Expr("now()"),
		})
	if res.Error != nil {
		return res.Error
	}
	if res.RowsAffected == 0 {
		return gorm.ErrRecordNotFound
	}
	return nil
}
```

同时给接口 `ProjectRepo` 加上签名。

### 3.2 `server/internal/service/project_service.go` — 封面规整 + 写入

```go
// SetCoverFromMaterial 把「某张素材图」设为项目封面。
//
// 职责边界：调用方（引擎）只负责挑出"该用哪张图"，这里负责把它变成
// 适合当卡片封面的地址（优先 640px 缩略图）并落库。
// 任何失败都只返回 error 供调用方记日志，不影响生成主流程。
func (s *ProjectService) SetCoverFromMaterial(ctx context.Context, projectID, rawURL string) error {
	cover := s.cardCoverURL(ctx, rawURL)
	if cover == "" {
		return errors.New("封面地址为空")
	}
	return s.projectRepo.UpdateCover(ctx, projectID, cover)
}

// cardCoverURL 优先返回约定式缩略图地址，缩略图不存在时回退原图。
func (s *ProjectService) cardCoverURL(ctx context.Context, rawURL string) string {
	if rawURL == "" {
		return ""
	}
	obj, ok := s.storage.ParseObjectName(rawURL)
	if !ok {
		return rawURL // 非本站存储（理论上不会走到）原样返回
	}
	thumbObj := ThumbnailObjectName(obj)
	if _, err := s.storage.StatObject(thumbObj); err == nil {
		return s.storage.GetURL(thumbObj)
	}
	return rawURL
}
```

`ProjectService` 已经持有 `storage.Storage`（构造函数里就有），无需新增依赖。

### 3.3 `server/internal/engine/executor.go` — 注入 + 调用点

**注入**：`VideoExecutor` 加字段 `projectCover *service.ProjectService`（engine 包已依赖 service 包，不引入循环依赖），`NewVideoExecutor` 与 `NewDefaultRegistry`（`executor.go:3477`）各加一个参数，`cmd/server/main.go:302` 传入既有的 `projectService`。

**调用点**：紧挨 `executor.go:2982` 的 `RecordGeneration`，理由完全一样 —— 同一个「产物确实已交付」的确信点、同一份 `detachedCtx`（不受执行超时影响）。

```go
// 项目卡片封面 = 这次生成视频所用的第一张素材图。
// 放在这里而不是"拿到上游 URL 就写"：只有走到这里才确定「钱花了、片子也落库了」，
// 中途失败不该改封面。同步写（一次 UPDATE，毫秒级），失败只记日志。
if projectID != "" && v.projectCover != nil && len(imageURLs) > 0 {
	if err := v.projectCover.SetCoverFromMaterial(detachedCtx(ctx), projectID, imageURLs[0]); err != nil {
		log.Printf("[VideoExecutor] 写项目封面失败（不影响出片）: projectID=%s err=%v", projectID, err)
	}
}
```

> `imageURLs` 的收集见 `executor.go:2475-2620`：mentions 里的图片节点 → 上游节点兜底 → 白模静帧。**取第 0 张**。首尾帧模式下第 0 张就是首帧图，天然正确。

### 3.4 P1（可选）：无素材图时抽一帧

纯文生视频 / 只有参考视频续写时 `imageURLs` 为空。此时可以从**已经在内存里的视频字节**抽首帧：

- 复用 `service.extractVideoFrameFile`（`video_frame.go:101`，纯函数，不碰网络与存储）；
- 复用 `service.GenerateImageThumbnail`（`thumbnail.go:15`）压到 640px；
- 上传到该节点的画布目录，把 URL 写为封面。

建议**异步 + 限一次**，别给交付路径加时长。代码位置同样在 `RecordGeneration` 附近，`go func(){...}()` 包一层即可。

## 四、前端改动清单

### 4.1 干掉 `picsum.photos`，改本地确定性占位

`web/src/components/project/ProjectCard.tsx:29-35`。兜底仍必须存在（存量项目回填完之前、以及纯文生视频项目），但要换成**零网络、稳定可辨识**的本地渲染：

```tsx
// 兜底封面：项目名首字 + 由 id 哈希出的色相，本地生成、零网络请求。
// 以前用 picsum.photos 随机图：与内容毫无关系，几个项目摆在一起完全分不清；
// 而且它是境外域名，大陆访问经常超时，卡片长时间空白。
function fallbackCover(project: ProjectListItem) {
  let h = 0;
  for (let i = 0; i < project.id.length; i++) h = (h * 31 + project.id.charCodeAt(i)) % 360;
  return {
    background: `linear-gradient(135deg, hsl(${h} 45% 32%), hsl(${(h + 40) % 360} 50% 18%))`,
    initial: project.name?.trim()?.[0] ?? '·',
  };
}
```

配色沿用现有暗色卡片风格（`from-black/90` 遮罩上是白字），首字用大号半透明字重。

### 4.2 类型与 API：无需改动

`coverUrl` 已存在于 `types/project.ts:6,17` 与 `services/projectApi.ts:21,33`，后端返回结构不变。

## 五、存量项目回填

### 5.1 为什么不能直接用 `generation_history`

`generation_history` 存的是**产物**（`model.go:588-601`），视频行的 `result_url` 是视频本身，**没有记录"用了哪张输入图"**。要复原"素材图"只能回到画布 JSON。

### 5.2 回填算法（与运行时同一条链路）

好消息：前端已经把 `mentions` 存在视频节点上（执行器就是读它收集素材的，`executor.go:2475`），所以回填不需要重新实现一套推断逻辑。

对每个 `cover_url = ''` 的项目：

1. 从 `generation_history` 取该项目 `node_type='video'` **最新一条**的 `node_id`（按 `created_at DESC`）；
2. 读该项目画布 JSON，定位该节点；
3. 遍历它的 `data.mentions`，取第一条 `nodeType == 'image'` 的引用，从对应图片节点的 `data.imageUrl` 拿素材图；
4. mentions 不可用（老画布/被清理）时，退化为按 `edges` 找上游图片节点；
5. 调 `ProjectService.SetCoverFromMaterial` 写入。

### 5.3 落地形态

照抄已有的 `/api/admin/media/backfill-thumbnails` 套路，新增：

```
POST /api/admin/projects/backfill-covers?limit=200&dry_run=1
```

- 幂等：只处理 `cover_url = ''` 的项目，可重复跑；
- 分页限速：一次 200 个，避免一次扫全表；
- `dry_run` 先出报告（将回填多少、跳过多少、无素材图多少），确认后再执行。

无素材图的项目，可选用 §3.4 的抽帧补上 —— 此时顺便把 `video_frame.go:627` 的 `WarmVideoSourceCache` 接上（它目前是**死代码**，注释写着"视频刚生成/上传完成时后台预热一次"，但全仓无调用）。回填视频抽帧要下载存量视频，务必限并发、后台慢跑。

## 六、边界与风险

| 场景 | 处理 |
| --- | --- |
| 多个视频节点并发完成 | 按**完成顺序**最后写入者胜，等于"最后一个生成完的视频"，语义正确；不需要时间戳防乱序 |
| 用户接着又改了别的（改名） | `UpdateCover` 只动 `cover_url` + `updated_at`，不整行覆盖 |
| 首尾帧模式 | `imageURLs[0]` 就是首帧图，天然正确 |
| 多图引用 / 白模静帧 | 取第一张；白模静帧也是用户认可的视觉 |
| 生成失败 / 已退费 | 只在 success 分支写，封面保持上一次的值，不会变空 |
| 纯文生视频（无输入图） | 走 §3.4 抽帧；未启用时不动封面 + 前端占位 |
| 项目被删除 | 走 `ProjectService.Delete` 同一套前缀清理，封面对象在画布目录内，天然被清掉 |
| 缩略图不存在（老数据） | `StatObject` 探活后回退原图；前端 `deriveThumbUrl` 另有回退 |
| 浏览器缓存 | 对象名是内容哈希（`thumbnail.go` 注释：sha256 前 12 位），换封面即换 URL，无需 cache-bust |
| `cover_url` 长度 | 列宽 500；ZOS 路径远小于此 |
| 隐私 | 封面是用户自己的产物，只写在用户自己的项目行上，不进 `shows/` 对外目录 |

---

## 七、验收标准

1. 新建项目 → 生成一条视频 → 返回首页，该卡片显示的是**这条视频所用的素材图**（不是随机图、不是空白）。
2. 同一项目再生成一条视频 → 卡片封面**跟随变为最新那条**的素材图。
3. 生成失败（含扣费退还）→ 封面**不变**。
4. 纯文生视频项目（无输入图）→ 卡片显示确定性占位，不出现 `picsum` 请求。
5. 网络面板中项目列表页**不再有任何对 `picsum.photos` 的请求**。
6. 存量项目跑一次 `backfill-covers`：dry-run 报告数量合理，正式执行后抽样 20 个项目的封面与画布中最后一次视频生成的输入素材图一致。
7. 最近有活动的项目排在列表前面（`projects.updated_at` 已随生成推进）。

## 九、备选方案与否决理由

| 备选 | 否决理由 |
| --- | --- |
| 前端实时从视频抽帧当封面 | 对象存储（天翼云 ZOS）**不返回 CORS 头**，跨域视频画进 canvas 会污染画布，`toDataURL` 直接抛 `SecurityError`。已在 `video_frame.go:23-28` 与 `show_handler.go:539-546` 记录过这个坑，服务端抽帧才是可行路径 |
| 前端按 canvas 内容本地算封面 | 画布 JSON 可能有几 MB，列表页拉 N 个项目再解析，流量与耗时都不可接受 |
| 让用户手动给项目设封面 | 增加操作成本，且反馈明确要求的是"自动显示上一次的素材图" |
| 每个视频节点生成时存一张专用封面对象 | 与已有的 `.thumb.webp` 约定重复，白白多一份存储 |
| 直接用 `generation_history` 回填 | 该表只存产物、不存输入素材，视频行拿到的 `result_url` 是视频而非素材图 |

### 10.1 与方案的偏差

- 封面写入放在**协程**里（方案里写的是同步）。原因：`cardCoverURL` 要调 `storage.StatObject`，
  而 ZOS/MinIO 的 `StatObject` 超时是 **5 秒**；同步执行时存储抖动会让"视频已生成"多等 5 秒才出现。
  代价是进程被强杀时这次写入会丢 —— 只影响封面，下一支视频会补。

### 11.1 与 §5 方案的三处修正

1. **加了游标分页**（方案里只写了 `limit`）。原因：回填是幂等的，**补成功的项目补完就从
   `cover_url 为空` 的结果集里消失了** —— 用 `offset` 翻页会跳行/重复；用 `id > cursor`
   不受集合收缩影响，且「补不上的项目」也不会把后续项目永远挡在分页后面。
2. **素材取值顺序比方案多一层**：mentions 的第一条图片引用优先用 **mention 自带的
   `imageUrl`**（前端预览用，方案里没提），取不到再回查那个图片节点。这样即使素材节点
   后来被删了、产物被清空，也还能对上。
3. **无生成历史时退化到画布**：方案假设 `generation_history` 一定有记录，但老项目大概率没有。
   此时取画布里**最后一个有 `videoUrl` 的视频节点**（节点数组大体按创建顺序追加）。

### 11.1.1 实施中新发现并修掉的一个坑：回填不能推 `updated_at`

第一版回填直接复用了运行时的 `UpdateCover`，而它会顺带把 `updated_at` 推到当前时间 ——
那是给「刚生成完视频」用的（项目确实刚活跃）。**回填动辄一次几百个历史项目，如果也推
`updated_at`，一次回填就能把所有老项目顶到「最近项目」最前面**，把用户真正在做的项目挤下去，
与这次要解决的问题正好相反。

所以拆成两个方法：运行时的 `UpdateCover`（推 `updated_at`）、回填的 `BackfillCover`
（只写 `cover_url`）。后者必须用 GORM 的 `UpdateColumn` —— `Update`/`Updates` 会自动写
`updated_at`。这条已用 `db.ToSQL` 干跑实测（GORM v1.25.11，无需连库）：

```
UpdateColumn → UPDATE "projects" SET "cover_url"='/media/x.png' WHERE id = 'p1'
Updates      → UPDATE "projects" SET "cover_url"='/media/x.png',"updated_at"='...' WHERE id = 'p1'
```

### 11.1.2 回填不会碰已有封面

`ListMissingCover` 只取 `cover_url` 为空的项目，所以**已经通过发布作品上传过封面的项目
不会被回填覆盖** —— 老项目的手动封面是安全的。

### 11.2 调用方式

```bash
# 1) 先干跑，看样例里取到的是不是那张素材图
curl -X POST -H "Authorization: Bearer <管理员token>" \
  'https://<host>/api/admin/projects/backfill-covers?limit=200&dry_run=1'

# 2) 确认后真跑；done=false 时把返回的 next_cursor 带进下一轮
curl -X POST -H "Authorization: Bearer <管理员token>" \
  'https://<host>/api/admin/projects/backfill-covers?limit=200&cursor=<next_cursor>'
```

返回 `{scanned, filled, no_video, no_material, failed, next_cursor, done, samples}`：
`samples` 最多 20 条，含 `project_id / node_id / source / material_url / cover_url / skipped`，
`source` 取值 `mention | mention_node | upstream`，`skipped` 说明为什么没写成
（`no_canvas / bad_canvas / no_video / video_node_gone / no_material / not_own_storage / update_failed`）。

与其他管理员维护接口一致，**没有做前端 UI**（`backfill-thumbnails` 也是 curl-only）。

`go build ./...`、`go vet`、`gofmt` 通过。两处关键行为都用临时测试实测过（测完已删）：

| --- | --- | --- |
| 有生成历史 + mentions 有图片引用 | 取历史节点的素材，写缩略图 URL，`source=mention_node` | ✅ |
| `dry_run=1` | 报告 `filled=1` 且给出 `cover_url`，但**不写库** | ✅ |

### 11.4 残留风险

- **回填是「按画布反推」，画布被后来的编辑改乱时可能取到不是当初那张图**（比如用户删了旧素材、
  换了一张再生成又撤销）。`dry_run` 的样例就是给这个用的，务必先抽样核对。
- **`no_material` 的项目不会被回填**（纯文生视频、素材节点已被删且 mention 没带 URL），

  没有对着真 PostgreSQL 跑过。上线后建议先 `dry_run=1` 看样例，再小 `limit`（如 5）真跑一轮，
  核对这 5 个项目的 `cover_url` 与 `updated_at`（**`updated_at` 必须没变**）再放量。
  → **已在 §12 完成线上验证，该风险已关闭。**

## 十三、第三批：封面改为「视频尾帧」，以及三个缺陷的修复（2026-10-28）

### 13.1 策略变更（用户给定，取代 §十/§十一 的「第一张素材图」）

封面的取值优先级改为：

1. **项目有视频 → 抽这条视频的最后一帧**；
2. 没有视频 → 用画布里的**最后一张图**；
3. 两者都没有 → 不写，前端渲染渐变占位。

为什么换：素材图回答的是「我用了哪张参考图」，卡片上经常和成片画面无关
（首尾帧、多图参考时尤其如此）；尾帧回答的才是「这条片子长什么样」。

### 13.2 抽尾帧为什么不能整片下载

源站（ZOS）总带宽约 1.26MB/s，一支 35.7MB 的片子整下要 30~200 秒；21 个项目那批
真跑要几十分钟。改用「远端 seek」：

- `probeDurationFromURL` 用 ffprobe **只读 mp4 头部**（`moov`）拿时长，几百毫秒；
- ffmpeg 把 `-ss <duration-0.5>` 放在 `-i` **之前**（输入侧 seek），只请求文件尾部那几个
  字节区间，解出一帧就停（`-frames:v 1 -f image2pipe -vcodec png pipe:1`），不落临时文件；
- PNG 走原有的派生资源链路落盘（原图 + 640px webp 缩略图），写进 `cover_url` 的是缩略图。

实测（35.7MB 视频）：

| 指标 | 值 |
|---|---|
| 后端容器 NET I/O 增量 | 128MB → 130MB（**≈2MB**，还含上传的产物，是上界） |
| 端到端耗时 | **1.595s**（整片下载法要 30~200s） |
| 21 个项目真跑 | **69 秒**（均摊 3.3s/个） |

**等价性验证**：旧法（整片下载 + `-sseof -0.5`）抽出的尾帧是 `89758614537c.png`，
新法（远端 seek）抽出的封面正是 `89758614537c.thumb.webp` —— 内容哈希一致，即**逐字节同帧**，
新法不是「近似」。首帧则是 `09357bf4715a`，确实不同（说明尾帧取到的不是片头）。
落盘对象按内容哈希命名，重复抽同一帧不会产生多余对象（实测重跑仍得 `945412ee20da`）。

两处兜底：`duration-0.5` 取不到就退到 `duration-1.5`；再不行退回整片下载法。
整个抽帧过程套 180 秒上限（`videoFrameCaptureTimeout`），保证不留野 ffmpeg 进程。

### 13.3 实施中发现并修掉的三个缺陷

**(1) 只试第一个视频候选就放弃。**
`latestVideoURL` 原先只取「生成历史里最新那条视频 → 否则画布最后一个视频节点」，
取到就抽、抽不出就降级成素材图。线上真实数据打脸：项目 `6c7d3b0a` 的生成历史里最新那条
`ca7c705cb40b.mp4` 已经 404，而画布里还有一个 206 的 `4ae276efcd80.mp4` ——
于是被误判成「没有可用视频」，封面退化成一张素材图（该项目的图后来也全 404 了）。
现在 `videoCandidates` 返回**按优先级排序、去重的候选列表**（历史最新 → 画布节点倒序），
`backfillOne` 逐个试，最多 3 个（`coverBackfillMaxVideoCandidates`）。

**(2) `cardCoverURL` 无条件回退原图，从不校验原图是否存在。**
它只探活缩略图，缩略图不在就把原图地址原样返回。项目 `6c7d3b0a` 整个画布的素材
（17 图 + 8 视频）在存储上只剩 1 个视频，结果写进去一个 **404 的 PNG 封面**。
现在原图也要 `StatObject` 探活，两者都不在就返回空串（宁可不写，也不写一个必然破图的地址）。
图片候选同样改成**从最后一张往前逐个找**，最多 8 张（`coverBackfillMaxImageCandidates`），
跳过对象已丢失的那些。

**(3) 干跑会报出已经死掉的候选。**
`dry_run` 不抽帧（抽了会落一个没人引用的孤儿对象），原先直接报第一个候选，
而它很可能正是被删掉的那个文件 —— 干跑看起来一切正常，真跑却一个个失败。
现在干跑会用 `StatObject` **只探活不下载**，跳过已不存在的候选。

### 13.4 线上执行结果（2026-10-28 22:16 ~ 22:50）
