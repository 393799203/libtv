# 多图参考编号排查（2026-11-04）

结论：存在应用侧参考图编号与用户理解不一致的路径。已通过执行真实
`ImageExecutor` 的参考图收集逻辑复现，在扣费及调用图像模型之前结束。
以下“复现”描述修复前的行为。后续已完成后端修复，验证详情见末尾；
测试使用模拟上游，没有调用真实图像模型或扣用户积分。

## 复现

用户显式引用顺序为人像、动作，另有一张连接的风格图：

| 用户理解 | 实际发给图像客户端的序号 |
| --- | --- |
| 图1：人像 | 图1：风格 |
| 图2：动作 | 图2：人像 |
| 风格图独立存在 | 图3：动作 |

原因是 `ImageExecutor` 先收集风格图和内容图，再以
`append(styleImageURLs, referenceImageURLs...)` 合并。即使用户只显式引用两张内容图，
上游连线中的风格图也会加入并排到最前。

另外复现了两处对应关系丢失：

1. `身份参考[[m:face]]，动作参考[[m:pose]]` 清理后变成
   `身份参考，动作参考`。`@` 标签的节点身份没有被转换为实际图号传给模型。
2. 提示词标记是 face、pose，但已有 mentions 元数据数组是 pose、face 时，
   后端按元数据数组发送 pose、face，不会按提示词中的标记重新排序。
   正常面板点击生成时会从 DOM 取引用顺序，因此这不是每一次普通编辑必然触发的情况；
   后端仍缺少对旧数据或其他生成入口的顺序校正。

图像客户端逐张转换 URL 或 base64，两种上游协议都保留传入顺序，
未发现这层做随机排序或反转。

## 影响与边界

以上足以造成“图1 的脸、图2 的动作”与模型实际收到的图片对应不上。
通用图生图包装提示词只说保持“参考图”的主体，没有明确每张图分别负责身份、姿态或背景。
因此即使图序正确，也没有应用层的逐图用途绑定。

未拿到用户描述的具体生成任务及输出，不能断言某一张已经生成的错误人脸一定由图序引起，
也不能把所有多图融合失败都归结为应用排序。

## 修复方向

- 将参考图节点、最终图片序号和用户可见编号统一成同一份映射。
- 将 `@` 标签替换成映射后的明确图号，不直接删去标签身份。
- 风格参考应明确标注编号和用途，避免悄悄插入后改变已有图号含义。
- 后端按提示词中首次引用顺序校正元数据，跨入口保持一致。
- 构造多图提示词时明确各图的用途，避免默认把所有参考图的主体都混合。

## 已实现

`server/internal/engine/image_references.go` 统一生成本次请求的参考图列表：

- 先按提示词中的引用出现顺序校正元数据，再按节点去重；同图不同引用标记均保留，
  并替换成同一个实际图号。
- 显式选择内容图时只使用被选中的内容图；隐式连接的风格图追加在末尾。
  用户显式引用风格图时仍尊重其在提示词中的位置。
- 未显式选择图片时，按内容图连线顺序兜底，再追加风格图。
- URL 从本次执行上下文的节点数据读取，不使用旧引用元数据里的预览 URL。
- 提示词 `@` 标记改写为“图1”等实际编号；发送时附带逐图名称与风格用途说明，
  用户指定单一身份来源时，禁止将仅用于动作、背景或风格的图片的人脸混入。
- 多图请求不再追加泛化的“保持所有参考图主体结构”要求。
  用户明确要求的人脸融合仍可执行。
- 缺失的显式参考图、损坏的引用信息在扣费前报错，避免跳过图片后悄悄改变图号。
- 元素编辑继续使用其专用的原图/裁剪图，不参与普通多图引用解析。

## 验证

已通过后端全量测试，以及引擎和模型客户端的 race 检查。
新增回归覆盖旧顺序、风格图、重复别名、连线兜底、预演静帧、最新 URL 和失效引用。

两条集成用例从真实 `ImageExecutor` 执行到模拟 HTTP 上游，分别检查 OpenAI 兼容
和 DashScope 多模态协议，均确认：

```text
图片数组：[人像、动作、风格]
用户指令：用图1的人脸和背景，图2的动作，再保持图1的身份
附加约束：图3只用于画风；不得擅自改变用户指定的人脸来源
```

这些测试验证应用发送的数据和对应关系，未评价图像模型最终生成的人脸一致性。
